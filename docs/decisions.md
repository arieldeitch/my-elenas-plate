## DEC-017 — חשבון Auth משותף אחד + שני פרופילים פנימיים (Supabase כמקור אמת)

- תאריך: 2026-07-23
- סטטוס: Accepted (מממש את DEC-001 ו-DEC-002)

### הקשר

נדרש Backend אמיתי לסנכרון בין מכשירים, אך ללא ניהול שני משתמשי Auth נפרדים לאריאל ולאלנה.

### החלטה

חשבון Supabase Auth **משותף אחד** למשק הבית, ותחתיו **שני פרופילים פנימיים** (אריאל/אלנה).
שני הפרופילים נגישים מאותו Session; ההפרדה היא לפי `profile_id`. אין למפות את אריאל/אלנה ל-`auth.users`.

### מימוש

- Migrations: schema (10 טבלאות, UUID, timestamptz, constraints), RLS (פונקציית `is_household_member`
  SECURITY DEFINER, 35 policies), `bootstrap_household()` idempotent, ו-Realtime ל-8 טבלאות.
- שכבות: client + generated types + repositories + auth + sync (offline queue, migration, realtime),
  משולבות ב-Store מאחורי דגל `isSupabaseConfigured()`; במצב דמו הכל אינרטי.
- `localStorage` יורד מלהיות מקור אמת — משמש רק ל-offline queue / cache / migration marker (מעדכן DEC-015).

### אימות

מול Supabase מקומי (CLI + Docker): כל ה-migrations הוחלו; בדיקת אינטגרציה חיה (5/5) אימתה bootstrap,
כתיבה/קריאה של שני הפרופילים מהחשבון המשותף, אילוץ הקפה, בידוד בין משקי בית (RLS) ודחיית קריאה אנונימית.

### השלכות / פתוח

- נדרשים `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY` (anon בלבד; לעולם לא service_role).
- אימות end-to-end בדפדפן (התחברות + realtime בין שני sessions) טרם בוצע אוטומטית — דורש credentials אמיתיים או הרצה מקומית.

## DEC-018 — סנכרון מאכלים מותאמים + מועדפים + אחרונים; `food_preferences.food_id` כ-text

- תאריך: 2026-07-23
- סטטוס: Accepted (מממש T-027; מרחיב DEC-017)

### הקשר

מועדפים/אחרונים/מאכלים מותאמים היו client-local. נדרש ש-Supabase יהיה מקור האמת גם עבורם, לשני סוגי
המאכלים: קטלוג מובנה (מזהי מחרוזת כמו `f_coffee`) ומאכלים מותאמים (UUID).

### החלטה

- מאכלים מותאמים נשמרים ב-`foods` (household-scoped, `is_active` ל-soft-delete). הקטלוג המובנה נשאר
  קבוע בצד הלקוח; החיפוש ממזג מובנה + מותאם.
- מועדפים/אחרונים ב-`food_preferences` לפי `profile_id` + `food_id`, כאשר `is_favorite` ו-`last_used_at`
  מגדירים מועדף/אחרון. `deriveFavoritesRecents` גוזר את הרשימות (אחרונים לפי `last_used_at` יורד, מוגבל ל-12).
- **Migration `20260723090400`**: `food_preferences.food_id` הפך ל-`text` (ללא FK) כדי שגם מאכלי קטלוג
  מובנים (מזהי מחרוזת) וגם מותאמים (UUID) יהיו ניתנים לסימון אחיד.

### מימוש

- `useSupabaseSync` מבצע hydrate/push ל-foods ול-preferences (dirty-tracking, optimistic, offline queue,
  realtime ל-`foods`+`food_preferences`), עם marker migration נפרד (`foods:v1`) כדי לתמוך במי שכבר הריץ
  את migration נתוני-הארוחות (v1).

### אימות / פתוח

- אומת חי (7/7 remote-live): יצירת מאכל מותאם, מועדפים/אחרונים לפי פרופיל, בידוד, soft-delete, realtime.
- **migration `090400` הוחל על ה-remote (2026-07-24)** ואומת: `food_id` הוא text, ולכן מועדפי/אחרוני
  **מאכלים מובנים וגם מותאמים** מסתנכרנים ב-remote (אומת בדפדפן, עם הפרדת פרופיל). הנתונים ההיסטוריים אינם נפגעים.

## DEC-019 — Supabase הוא מקור האמת לקטלוג; מודולי TypeScript הם ההגדרה הקנונית ו-Fallback

- תאריך: 2026-07-25
- סטטוס: Accepted (מממש DEC-001; מרחיב DEC-018)

### הקשר

הקטלוג המובנה היה קבוע בצד הלקוח (23 פריטים) ורק מאכלים מותאמים נשמרו ב-`foods`.
נדרש קטלוג עברי רחב לשימוש יומיומי, וגם ש-Supabase יהיה מקור האמת (DEC-001) —
בלי לשבור את היכולת לתעד כאשר ה-Seed עוד לא הוחל או כשאין רשת.

### החלטה

- **הגדרה קנונית**: מודולי TypeScript לפי קטגוריה תחת `src/data/foods/*.ts` (390 פריטים).
- **מקור אמת בזמן ריצה**: `public.foods`. `mergeCatalog` ממזג לפי `normalized_name`:
  שורה מרוחקת **גוברת** על הפריט המובנה (category / default_unit / kind), שורה עם
  `is_active = false` **מסתירה** אותו, ושורות ללא התאמה הן מאכלים מותאמים.
- **`id` נשאר ה-`f_*` של הקטלוג** גם כשהשורה המרוחקת גוברת, כדי שמועדפים/אחרונים
  (`food_preferences.food_id` כ-text, DEC-018) לא יתנתקו כשה-Seed מוחל.
- **Fallback**: כל עוד אין שורה מרוחקת, הפריט המובנה מוצג — כך האפליקציה שמישה
  offline, לפני החלת ה-Migration, ובמצב דמו מקומי.
- **סנכרון SQL↔TS**: ה-Seed ב-Migration נוצר מהמודולים ע"י `npm run catalog:seed`
  (`scripts/generate-catalog-seed.ts`), ו-`src/lib/catalog-seed.test.ts` נכשל אם הקובץ
  אינו הצורה המעודכנת. אין אפשרות ל-drift.

### חלופות שנשקלו

- להשאיר את הקטלוג רק בצד הלקוח — נדחה: סותר את DEC-001 ואינו נגיש ל-DB.
- להעביר את הקטלוג רק ל-DB — נדחה: לפני החלת ה-Seed / ללא רשת האפליקציה תישאר בלי
  קטלוג, ו-`f_coffee` (DEC-014) חייב להישאר קבוע בקוד.
- להוסיף עמודת `catalog_key`/`allowed_units` ל-`foods` — נדחה: שינוי Schema שאינו נדרש.
  `allowed_units` אינו קיים ב-Schema; קבוצות היחידות נשארות בצד הלקוח.

### השלכות

- `foods.is_active` נטען כולל שורות מאורכבות (`loadFoods` ללא סינון) כדי ש-Archive
  ב-DB אכן יסתיר פריט מובנה. `Food.isActive` נוסף ל-Domain.
- `mappers.foodToRow` משתמש ב-`normalizeFoodName` (DEC-020) עבור `normalized_name`.
- קבצים: `src/data/foods/*`, `src/lib/food-catalog.ts`, `src/lib/domain.ts`,
  `src/lib/supabase/{mappers,repositories}.ts`, `src/lib/sync/use-supabase-sync.tsx`,
  `scripts/{catalog-seed-sql,generate-catalog-seed}.ts`.

## DEC-022 — אירועי Realtime חייבים להיבדק ברצף, לא במקביל

- תאריך: 2026-08-01
- סטטוס: Accepted

### הקשר

בבדיקת T-034 נכשלה באופן עקבי הבדיקה
`realtime: a second context sees insert, update and delete`
מול Supabase מקומי, בעוד ששאר 11 הבדיקות ה-live עברו.

אבחון מבודד (broadcast מול postgres_changes) הראה:

- ה-WebSocket תקין (`SUBSCRIBED`, broadcast נמסר).
- ה-publication מוגדר נכון על כל שמונה הטבלאות.
- `REPLICA IDENTITY FULL` **אינו** הפתרון — נוסה ונפסל.
- כאשר מוסיפים השהיה בין הפעולות, שלושת האירועים נמסרים.

### הסיבה

Realtime מבצע את בדיקת ה-RLS עבור אירוע `postgres_changes` מול **מצב השורה הנוכחי** במסד הנתונים.
כאשר `insert` → `update` → `delete` מבוצעים ברצף מהיר ללא המתנה, ה-`delete` מגיע לפני שרשומת ה-WAL
של ה-`update` עובדה. בשלב זה השורה כבר נמחקה, בדיקת ה-RLS אינה מוצאת אותה, ואירוע ה-`UPDATE`
מושמט בשקט.

זו הייתה תקלה בבדיקה בלבד — **לא תקלה במוצר**. Realtime עצמו תקין.

### החלטה

בדיקות Realtime ימתינו לכל אירוע לפני ביצוע המוטציה הבאה, במקום לבצע את כל המוטציות ואז להמתין
לשלושת האירועים יחד.

### נימוק

הבדיקה הקודמת הייתה תלוית תזמון: היא עברה מול פרויקט מרוחק מהיר ונכשלה מול סביבה מקומית עמוסה.
המתנה לכל אירוע הופכת אותה לדטרמיניסטית. כתוצאה מכך זמן הריצה ירד מ-85 שניות (timeout) ל-3.7 שניות.

### השלכות

- אין שינוי ב-Schema, ב-RLS או בקוד המוצר.
- קוד מוצר שמסתמך על אירוע `UPDATE` מיד לפני מחיקה אינו יכול להניח שהאירוע יגיע.
- `supabase/migrations/20260723090300_realtime.sql` נותר ללא שינוי.

  Supabase; בלעדיהן `RuntimeGate` מציג דף חסימה במסך מלא (גם ב-SSR), ה-store וה-auth אינם נטענים,

- **Preflight להרצה:** `npm run preflight -- --env | --local | --live` — בדיקה קריאה-בלבד שנכשלת
  (exit 1) על כל בנייה שאינה האפליקציה המשותפת המחוברת. מול האתר החי ב-2026-09-18: FAIL, כצפוי.

### השלכות

דשבורד ארוך (כרטיס תאריך, כרטיס השלמה גדול, שש משבצות גבוהות בשני מסכים), והוספת מאכל רגיל דרשה
5–6 הקשות עם קפיצה בין מסך "רשימה" למסך "חיפוש" וללא משוב על מה שנוסף.

### ההחלטות

1. **היררכיית הבית:** כרטיס "אני" (`TodayCard`: שם + צבע אישי, תאריך עם ניווט, פס התקדמות,
   "לאחרונה: מאכל · ארוחה · שעה") → כרטיס בת/בן הזוג (`PartnerGlance`) → שש משבצות הארוחות
   הקומפקטיות (הפעולה). כל השישה נכנסים למסך אחד ב-Pixel 7 וב-360px.
2. **בלי קלוריות/מאקרו בכרטיס בת/בן הזוג.** נבחן ונדחה: DEC-004 ו-PRD שוללים ספירת קלוריות,
   ובמודל הנתונים אין ערכים תזונתיים כלל — לא מייצרים נתון שאינו קיים. הכרטיס מציג שם, שש נקודות
   סטטוס, המאכל האחרון (שם + ארוחה + שעה), וצום/אימון רק כשהיום מכיל אותם.
3. **שורת "לאחרונה" בבית מותרת** (שם מאכל אחד, בלי כמות ובלי רשימה). ההנחיה "בלי פרטי מזון על
   המשבצות" נשארת בתוקף למשבצות עצמן.
4. **מסך עריכת ארוחה אחד:** הרשומות הקיימות למעלה, חיפוש/מועדפים/אחרונים מתחת. ארוחה ריקה נפתחת
   ישר לחיפוש. כמות וקפה הם צעדים, לא מסכים.
5. **הוספה בהקשה אחת מ-מועדפים/אחרונים** בכמות הרגילה (1 × יחידת ברירת המחדל של המאכל) עם
   "עריכת כמות" ב-toast; תוצאת חיפוש שהוקלדה ומאכל ללא יחידת ברירת מחדל עדיין שואלים כמות.
   הזרימה הרגילה: משבצת → צ׳יפ → סיום (2 הקשות + סגירה) לעומת 5–6 קודם.
6. **בעלות:** צבע אישי קבוע לכל אחד (ירוק אריאל, כחול אלנה) ב-`PROFILES`; כותרת העורך "ארוחה · שם"
   עם אווטאר ופס עליון בצבע; `data-owner` על כרטיס היום ועל הדיאלוג לבדיקות.
7. **אמון:** מחוון הסנכרון שקט כשהכול מאושר ("מסונכרן" כטקסט עמום; "נשמר במכשיר" בבניית הדגמה),
   pill רק כשנדרשת תשומת לב, שגיאה בולטת עם "נסיון חוזר". "מסונכרן" מוצג רק כשהתור ריק ו-Supabase
   אישר כל פעולה (ללא שינוי בסמנטיקה מ-M1).
8. **`FoodEntry.loggedAt`** — נקרא מ-`created_at`, נחתם מקומית בהוספה, לעולם לא נכתב; משמש רק
   ל"לאחרונה".
9. **ה-FAB** פותח את המשבצת הריקה הראשונה, לא תמיד "ארוחה מרכזית".

### השלכות

- `DateNavigator` ו-`DailyCompletionIndicator` הוסרו (הבדיקות הועברו ל-`TodayCard`).
- ה-e2e של הענף המבודד (`e2e/helpers.ts`, `e2e/crud.spec.ts`) הותאם לזרימה החדשה; יש להריצו מול
  הענף בריצה הבאה שיש לה גישה.
- באנר השקילה הקבוע נשאר כפי שהוא — מועמד לצמצום ב-M2 שלב ב׳.

אחרי DEC-026 נותרו בבית באנר שקילה קבוע שצף מעל המשבצות ושני כרטיסי עורך מלאים (אימון, צום) שתפסו

## DEC-028 — M2-4 סקירת היום: גיליון קריאה-בלבד לשני בני הזוג; עריכה רק לאדם הפעיל; מעבר מפורש לעריכת בת/בן הזוג

**תאריך:** 2026-09-18 · **סטטוס:** מאושר · **ריצה:** `docs/claude-tasks/RUN_2026-09-18_M2_4_DAY_REVIEW.md`

### הקשר

הבית ענה על "כמה תיעדתי" ו"מה תיעדתי לאחרונה", אבל לא על "מה בדיוק אכלתי היום" — לכך נדרשו שש
פתיחות של משבצות; לראות את היום של בת/בן הזוג דרש החלפת פרופיל ואותן שש פתיחות.

### ההחלטות

1. **`DayReview`** — bottom sheet (אותה תבנית כמו עורך הארוחה) עם תאריך, "n/6 ארוחות תועדו · k פריטים",
   מתג "שלי / אלנה" בצבעים האישיים, ושש המשבצות בסדר קבוע: רשומות כ"שם · כמות · HH:mm" (שעה רק
   מ-`loggedAt` אמיתי; אין המצאת זמנים), "לא נאכלה ארוחה" למשבצת שדולגה, "לא תועד" עמום למשבצת ריקה
   — תמיד שש שורות, בלי קפיצות פריסה בין מצבים.
2. **מקור הנתונים** — ה-store בלבד (שני הימים של התאריך הנבחר כבר מוטענים על ידי הבית, M2-2). אין
   קריאות חדשות, אין realtime חדש.
3. **נקודות כניסה** — הקשה על אזור ההתקדמות/"לאחרונה" בכרטיס היום ("כל היום"), והקשה על כרטיס בת/בן
   הזוג פותחת ישירות את הסקירה שלו/ה. המשבצות ממשיכות לפתוח את העורך (תיעוד מהיר נשמר כפי שהוא).
   הקשה על ה-pill שבמשבצת לא הוקצתה לסקירה — מודל אחד: משבצת = תיעוד, כרטיס היום = סקירה.
4. **בעלות ועריכה** — עיפרון לכל משבצת מופיע רק כשהאדם הנסקר הוא הפרופיל הפעיל, ופותח את
   `MealEditor` הקיים (אותו אדם, אותו תאריך, אותה משבצת; הסקירה נסגרת). היום של בת/בן הזוג נסקר
   קריאה-בלבד; כפתור תחתון מפורש "מעבר לפרופיל של … (לעריכה)". כלל המוצר הקיים לא השתנה: החשבון
   המשותף רשאי לערוך את שני הפרופילים (DEC-017) — הסקירה פשוט אינה הופכת זאת למקרי. **צפייה לעולם לא
   משנה את התאריך הנבחר או את הפרופיל הפעיל.**
5. ההמלצה הקודמת "הקשה על ה-pill של המשבצת פותחת סקירה" נדחתה כדי לא ליצור שני מודלי אינטראקציה.

### השלכות

- כרטיס בת/בן הזוג: הקשה = סקירה (לא החלפת פרופיל). ההחלפה זמינה מהמתג בכותרת ומתחתית הסקירה.
- ה-e2e ההרמטיים שהחליפו פרופיל דרך הכרטיס עודכנו לצעד המפורש.

## DEC-029 — M2-5 כמות בהקשה אחת: − / + רק ליחידות ספירה, צעד 1, לעולם לא מתחת ל-1

**תאריך:** 2026-09-18 · **סטטוס:** מאושר · **ריצה:** `docs/claude-tasks/RUN_2026-09-18_M2_5_QUANTITY_STEP.md`

### הקשר

ההוספה המהירה (DEC-026) רושמת תמיד "1 × יחידת ברירת המחדל". התיקון השכיח ביותר — 2 ביצים, 2 פרוסות —
דרש עיפרון → מסך כמות → אישור (3 הקשות).

### ההחלטות

1. **יחידות ספירה בלבד נתמכות ב-stepper:** יחידה, חצי יחידה, כף, כפית, כוס, ספל, פרוסה, קערה, מנה
   (`COUNT_UNITS`). צעד 1; שבר נשמר (1.5 → 2.5). **יחידות משקל/נפח** (גרם, ק״ג, מ״ל, ליטר), כמויות
   סובייקטיביות ורשומות חריגות נשארות עם העורך המלא (עיפרון) — אין המצאת סמנטיקת צעד ליחידות אלה.
2. **רצפה 1:** "−" מושבת כשהתוצאה תרד מתחת ל-1. `1 → 0` לעולם לא מוחק; מחיקה נשארת פעולה נפרדת (פח).
3. **קפה** בכוסות/ספלים הוא יחידת ספירה → נתמך, וסיכום הקפה נשאר גלוי.
4. **רבים בעברית** בתצוגת כמות (`formatQuantity`): "2 יחידות", "3 פרוסות", "1,5 כוסות"; `1` נשאר יחיד;
   יחידות שאינן ספירה ללא שינוי ("150 גרם").
5. **שמירה:** אותו מסלול כמו כל עריכה (`updateEntry` → `entry.upsert`); הקשות מהירות מתמזגות בתור
   העמיד לפי מפתח הרשומה לפעולה ממתינה אחת וכתיבה אחת עם הכמות הסופית (מנגנון קיים, הוכח בבדיקה).
   ה-UI אופטימי; "מסונכרן" מוצג רק אחרי אישור.
6. **שורת רשומה בשתי שורות** (שם + פעולות נדירות / כמות) כדי ששמות ארוכים יישארו קריאים; השורה
   שנוספה זה עתה מודגשת; ה-toast הוא אישור בלבד.
7. **סקירת היום** משתמשת באותו עיצוב כמות ואינה מקבלת steppers — היא לקריאה.

### השלכות

- שמות נגישות של פעולות בשורה כוללים את שם המאכל ("עוד ביצה קשה", "מחיקה: תפוח").
- הזרימה הנפוצה "2 ביצים": משבצת → צ׳יפ → + → סיום = 4 הקשות (היו 6).
