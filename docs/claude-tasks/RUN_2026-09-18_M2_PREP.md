## 2. Deployment-configuration ambiguity — resolved (DEC-025)

Investigated how Lovable really delivers frontend `VITE_*` values (Lovable docs: "Deploying and
hosting outside Lovable" and the Supabase-integration pages). Finding: Lovable's Supabase integration
writes `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID` into a
**`.env` file in the project code**; there is **no** project-settings UI for custom frontend env. This
repo git-ignored every `.env*` file and read only `VITE_SUPABASE_ANON_KEY` — so **no Lovable build
could ever have been configured**. That is the structural root cause behind DEC-024, and the previous
run's instruction ("set env vars in the Lovable project settings") would not have worked.

Changes (`a99f531`):

- **`.env.production` committed** (un-ignored): `VITE_SUPABASE_URL=https://rqgoiuztphkcvbwtbxbj.supabase.co`,
  `VITE_RUNTIME_TARGET=shared`, and a commented `VITE_SUPABASE_ANON_KEY=` line for the owner. Public
  values only; the preflight fails on a `service_role`/`sb_secret_` key. Local `.env` stays private.
- `src/lib/supabase/client.ts` accepts `VITE_SUPABASE_PUBLISHABLE_KEY` as an alias (so Lovable's
  "Connect Supabase" path also yields a connected build); `vite.config.ts` + preflight know both names.
- `docs/RUNTIME_CONFIG.md §3` rewritten; `supabase/DEPLOY.md`, `docs/todo.md` (M1-R1 now mechanical),
  `docs/claude-context.md`, DEC-025.
